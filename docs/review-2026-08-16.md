## Vehicles (agent: rev-vehicles)

### 1. Dying in a vehicle burns the seat permanently — VERIFIED
`game/PlayerController.cs:3819` `EjectFromVehicleOnDeath()`

`Vehicle.OccupiedSeats` is only ever `Remove`d in two places — `TrySwitchSeat` (`:5657`) and
`ExitVehicle` (`:5684`). Confirmed by grep: the only mutation sites are `Add` at `:5634` and those
two removes. The death path nulls `_driving`/`_riding` and restores the body but never frees the
seat.

Failure: die in a single-seat vehicle (tractor, minicopter, skycrane, semi, tank — all `SeatCount
== 1`) from anything that is not the vehicle's own explosion, and `OccupiedSeats` keeps `{0}`
forever. The next `EnterVehicle` scan (`:5631`) walks off the end, hits `_seatIndex >= SeatCount`,
and returns with `_driving = null` — the vehicle is silently un-enterable for the rest of its life.
On a multi-seat vehicle, dying in seat 0 loses the *driver's* seat: everyone afterwards boards as a
passenger and `TrySwitchSeat(0)` is refused.

Why it was easy to miss: the explosion path is fine — `DriveVehicle` (`:5738`) calls `ExitVehicle()`
first, which frees the seat, and only then applies the damage.

### 2. A turret gunner's left click honks the horn — VERIFIED
`game/PlayerController.cs:4263`

`if (_driving != null) _driving.Honk();` with no seat check, and `_riding != null` is an explicit
no-op. Confirmed by tracing the callers: `Fire()` is reached only from `StartFire()` (`:4276`, the
`else` branch, which requires being on foot) and the auto-fire poll (`:5962`, gated on
`FireMode.Auto`). `FireTurret()` (`:4825`) is called only from `Fire()` (`:4644`). So the gunner
branch is correct code that nothing can reach through input.

Failure: take the Hind's nose-gunner seat, aim the chin gun (aiming works), click — the helicopter
honks. `HeliPartsTests` calls `TryTurretFire` on the `Vehicle` directly, so the input routing is
never covered by a test.

### 3. Every helicopter renders as a jeep on remote clients — VERIFIED
`game/Vehicle.cs:1878` `SpecFor`

`SpecNames` (`:1874`) has 28 entries; `SpecFor`'s switch covers 18 of them and falls to `_ => _jeep`.
Missing: `minicopter, huey, scoutcopter, hind, orca, skycrane, hummingbird, apc, runabout`.

### 4. The wheel-derived centre of mass is a dead store — VERIFIED
`game/Vehicle.cs:2538`

```csharp
float comY;
if (s.Wheels.Length > 0) { comY = 0f; foreach (var wl in s.Wheels) comY += wl.y; comY = comY / s.Wheels.Length - 0.2f; }
if (s.Tracked) comY = TankComY;
else comY = s.BoxCenter.Y - s.BoxSize.Y * 0.25f;   // BOAT (no wheels)
```

The second statement is a separate `if`, not an `else if`, so its if/else assigns on every path and
the wheel average is never used. It compiles clean because definite assignment is satisfied by the
second block.

Effect: every wheeled vehicle carries a COM 0.13–0.30 m higher than the formula computes, and on the
wrong side of the axles — the top-heavy condition the comment says it was fixing. Jeep intended
0.05, actual 0.351. Bus intended −0.12, actual 0.107. Boats and helis are unaffected (the `else` is
the correct branch when `Wheels.Length == 0`); the tank is deliberately overridden.

`game/PlayerController.cs:4770` — `spread = 0f;   // superseded`

## Netcode (agent: rev-netcode)

### 1. The join snapshot's length is a UInt16, the composer's budget is ~150 KB — VERIFIED
`core/UnturnedNet/NetWorldHost.cs:363`

`Compose(..., maxBytes: NetProtocol.MaxReliableMessageBytes / 2)` — and
`MaxReliableMessageBytes ≈ 301 kB`, so the composer may legitimately produce ~150 KB. The frame then
declares it as `w.WriteUInt16((ushort)snapshot.Length)`, which saturates at 65,535. A 2.3×
disagreement between what the producer may emit and what the frame can describe.

Failure: a snapshot ≥64 KiB is framed with a truncated length; the client reads the short length,
`SnapshotApplier.Apply` walks a block past the buffer and returns false, `LastAppliedServerTick`
stays 0, the ack is never sent, and `TickReplication` skips that peer **forever**. The reliable
channel already delivered the message, so nothing retransmits. The player sits on "connecting"
indefinitely. Lengths that are exact multiples of 65536 truncate to 0 and die on the `len == 0`
guard instead — same wedge. The starvation-recovery full uses the identical path, so an
already-playing client wedges the same way.

The defect is confirmed; whether today's PEI content already crosses 64 KB is not — the agent said
so explicitly and named the reachable path (deployable accumulation, ~20 B/entity).

### 2. The session clock never advances while connecting — VERIFIED
`core/UnturnedNet/NetClientSession.cs:86-99`. Only the `Connected` branch calls `_session.Tick(_tick)`;
the `Connecting` branch does not. So every Connect datagram is stamped `SendTick = 0` and the first
RTT sample equals the client's absolute tick count. An Accept landing at tick 200 yields
`SRTT = 200` → `RTO = 300 ticks = 6 s`, precisely during the join, when the join snapshot is being
fragmented. A single lost fragment then waits 6 s for its first retransmit. Decays over the following
~30 acks, so only the join window is affected.

### 3. `UdpClientTransport.Send` has no `SocketException` guard — VERIFIED
`core/SDG.NetTransport/UdpNetTransport.cs:147`. `public void Send(...) => _socket.SendTo(...)` on a
**non-blocking** socket. `NetSession.Admit` blasts every fragment back-to-back with no pacing, so a
near-budget join snapshot is >100 datagrams in one loop and can hit EAGAIN/ENOBUFS. The throw unwinds
through `Transmit → Admit → TickReplication → SimRoot.Frame`, abandoning that tick's replication for
every remaining peer.

The tell that makes this a real oversight rather than a judgement call: `ReplyStatus` at `:110`
*does* wrap its `SendTo` in `catch (SocketException) { }`. The hazard was handled at the one call
site that doesn't carry game traffic and missed at the two that do.

### 4. The client accepts datagrams from any source — VERIFIED
`core/SDG.NetTransport/UdpNetTransport.cs:149-160`. `Receive` fills `EndPoint from` and never
compares it to `_server`. The server side is protected by construction (peers are keyed on the
connection); the client has no equivalent filter. One spoofed 12-byte Control/Disconnect datagram to
the client's ephemeral port drops the player. A spoofed UnreliableSequenced datagram is worse — it
advances `_lastUnreliableSeq`, so the real server's subsequent snapshots are dropped as stale.
Needs the 16-bit source port, which an on-path attacker has for free.

### Clean, per the agent — and this is the load-bearing part
Every `Write`/`TryRead` pair and every `WriteFull`/`WriteDelta`/`ReadSnapshot` triple in
`core/UnturnedNet/` was machine-diffed field-by-field: **zero width or ordering asymmetries.**
Command ids 0–35 have no collisions and no gaps, every id the client sends has a registration, and
every state-mutating command carries a `validate:` except the deliberate grid-is-the-validator cases.
The fragment/reassembly bounds, ack wrap arithmetic, and disconnect fan-out all hold.

Two items were deliberately dropped as padding, with reasons — a ~2-byte budget overshoot the agent
could not make reachable, and a `_gunByPlayer` disconnect leak that belongs to another agent's scope.

## Inventory / items / attachments (agent: rev-inventory)

This is the largest cluster, and it shares one root cause with the dupes already fixed this week:
**a client-local grid mutation with no net command, silently reverted (or refunded) by the next owner

*every page cell-for-cell* from the replica, and `Main.ResolveLoopbackMode` returns
`(attach: true, consume: true)` for every real SP entry, so this is live in singleplayer, not just MP.

Also verified: the registered command set is UpgradeSkill, Place/Salvage/PickupDeployable,
ExtractFuel, Connect/RemoveWire, ToggleDeployable, ToggleDoor, SetDoorLocked, ClaimBed, MoveItem,
DropItem, PickupItem, EquipItem, Craft, Consume, FitAttachment, Open/CloseStorage, Console,
Plant/HarvestCrop. **There is no reload command, no magazine command, and no clothing command.**

### 1. Reloading refunds the magazine — VERIFIED
`game/PlayerController.cs:3411` (`DoMagSwap`), `:3466` (`ConsumeShells`), `:3512`, `:3623`

`DoMagSwap` does `Inventory.items[fb].removeItem(fi)` and `Inventory?.tryAddItem(new Item(...))`
directly, reached unconditionally from the reload completion tick with no `InventoryIsServerOwned`
branch and no command behind it.

Failure: one full magazine in the bag. Fire dry, press R — the client spends it. The server grid is
untouched. Pick up anything, drop anything, open a crate — that dirties the server entry, the owner
block goes out, and the full magazine is back. Reload again for another free 30. Identical for
shotgun shell stacks.

### 2. The owner echo orphans the held item — VERIFIED (mechanism)
`ReadSnapshot` builds a fresh `PlayerInventory` with `new Item(...)` per jar on every snapshot, and
`AdoptReplicatedInventory` re-seats *those* objects into the shell's pages. `_heldItem` is only
assigned at equip time and keeps pointing at the pre-echo object — and `SaveGunState()` is the sole
writer of gun ammo/chamber/firemode/mag/attachments.

Consequences the agent traced: holstering writes ammo into a dead object, so re-equipping restores
30/30 free; `IsHeld` is a `ReferenceEquals`, so after the first echo the gun in your hands offers
"Equip" instead of "Dequip" and dropping it leaves the viewmodel up; a gas can filled server-side
reads empty because `_heldFuelItem` points at the orphan.

**Separate defect in the same handler — VERIFIED.** `OnExtractFuel`
(`core/UnturnedNet/ServerTransactions.cs:427`) does `can.fuelLevel = ... + pulled` — a bare field
write on an `Item`. `PlayerEntry.Dirty` is set only by `Items.onStateUpdated` (hooked at
`InventoryReplication.cs:251` to add/remove/resize) and the two storage open/close sites, so a field
write raises nothing and `WriteDelta` emits an empty block. The fill is **not echoed at all** until
some unrelated grid change dirties the entry. The code's own comment at step (4) states the intent
the mechanism doesn't deliver: *"owner echo carries the fuller can back to the client"*.

The agent's explanation for why `unify.gaspump_fixture_extract` is green anyway — its `give` dirties
the entry a tick or two before the extract — it correctly labelled PLAUSIBLE rather than confirmed.

### 3. Attachments are stripped by every echo — VERIFIED
`core/UnturnedNet/InventoryReplication.cs:386-433`

`WriteJar`/`ReadJar` carry `gunAmmo`, `gunFiremode`, `gunMagId`, `gunAttach`, fuel and fluid state —

`gunChamberedType` or `gunAttachSeeded`, all of which exist on the item

re-equip: the scope is gone from the gun **and** from the bag — destroyed, not duplicated. This is

### 4. Consuming from a crate or the ground is free — VERIFIED
`game/PlayerController.cs:1999`

`FindBagCell` is the only bag scan in the codebase that loops `p < PlayerInventory.PAGES` (all 9);

finds the jar, passes the consumable check, **removes nothing**, and still applies the health and

### 6. Clothing equip/unequip is entirely client-local — VERIFIED

### 7. The Store/Take quick-move never reaches the server — REPORTED

## World / terrain / deployables / fluid (agent: rev-world)

### 1. One smashed hydrant kills all fluid on the map, permanently — VERIFIED
`game/FluidNet.cs:205`

The pump-lift relaxation indexes `ceiling[a]` / `ceiling[b]` unguarded. `rawHoses` is built from the
`"hoses"` group; `ceiling` is keyed only off `"fluid_devices"`. **The guard exists in the sibling
function 95 lines up** — `WouldNeedPump` at `:110` does
`if (!ceiling.ContainsKey(a) || !ceiling.ContainsKey(b)) continue;` over the identical link list.
`Tick` is the copy that dropped it.

Failure: hose a fire hydrant to a fluid pump, then shoot the hydrant. `SetBroken(true)` removes it
from `"fluid_devices"`; nothing removes the hose. Next tick, `ceiling` has no entry for the hydrant,
`b.IsFlowRelay` is true, `ceiling[a]` throws. `FluidManager._Process` dies **every frame thereafter**,
so every pump, tank, purifier, sink and fuel inlet on the map stops moving fluid — not just the
smashed line.

### 2. Felled trees come back as billboards — REPORTED
`game/ResourceField.cs:63`. `SetAlive` rewrites only the slots in `InstanceRec.Slots`, populated
solely by the real-mesh loop; the far-field impostor MultiMeshes never register theirs. Walk past
~211 m and every felled tree reappears as a billboard, out to 2000 m. A cleared logging area looks
cleared up close and untouched from a ridge.

### 3. Power switches are inert in multiplayer — REPORTED
`core/UnturnedNet/DeployableReplication.cs:520`. `Solve()` builds `new PowerDevice { ... }` and never
sets `Conducting`, which defaults true — so the replicated graph treats a switch as permanently
closed. `CanToggle` then refuses the toggle because `FuelCapacity <= 0`. SP is correct
(`PowerNet.cs:101` passes `Conducting`), so identical wiring behaves differently in SP and MP, and
`StateHash` hashes entity inputs rather than solver outputs, so parity cannot see it.

### 4. Picking up a hosed deployable leaks the hose — REPORTED
`game/Deployable.cs:526`. Pickup/salvage/wreck-despawn free power wires but never fluid hoses; only
`FluidContainer.Pickup()` does that. The hose is parented to the world root, so it stays in the
`"hoses"` group rendering in mid-air attached to nothing — one per pickup, forever. With a relay
fitting in the line this becomes finding 1's crash instead of a leak.

### Sweep 1 — walkers that silently skip a subtree: NO CONFIRMED BUG, but a shared risk
Six extractors carry an identical name-keyed subtree skip (`{"dead","ragdoll","effect","nav",
"block","trap"}`, all `return` — the whole subtree, not the node). That is exactly the `"Wheels"`
shape that cost two helicopters their landing gear, and it fails just as silently: `lod0_gos` selects
renderers off the LODGroup then requires `if (gp in gomap)`, so any LOD0 renderer under a skipped
node is dropped with no error. All six sets are byte-identical, which at least rules out drift.

The agent **could not demonstrate a real prop losing geometry** without a local Unturned install, and
said so rather than claiming a bug. The cheap check for whoever has the install: per prop, diff
`lod0_gos`' renderer count against the LODGroup's declared LOD0 renderer count and print any
disagreement.

## Main / UI / editor / rendering (agent: rev-ui)

### 1. `vertexlight` cannot reach the renderers that dominate the frame — REPORTED, and it blocks the lighting evaluation
`game/GraphicsOptions.cs:76`

`ApplyShading`'s walk descends only into `node is MeshInstance3D` and mutates only
`StandardMaterial3D`. That excludes **`MultiMeshInstance3D`** — which derives from
`GeometryInstance3D`, not `MeshInstance3D` — so every tree, rock, pebble and grass patch is skipped;
and it excludes the **terrain** and **grass**, both `ShaderMaterial`. The console then prints
"N material(s) changed" and warns only when N == 0.

So `vertexlight on` converts the placed-prop set (large N, reads as success) and leaves terrain, all
trees/rocks and all grass on per-pixel. **Any A/B measurement through the current switch is a lower
bound of unknown tightness** — and would read as "vertex lighting barely helps", which is the
conclusion strawberry is trying to test. This needs fixing before the GPU test is worth running.

### 2. Deleting a placed loot crate / shelf / gas pump is unrecoverable *and* desyncs undo — REPORTED
`game/EditorObjects.cs:515`. `DeleteSelected` builds its undo capture only from nodes carrying a
`"guid"` meta, but the delete loop frees everything in `_selection`. Loot crates, store shelves,
grid-power boxes, gas pumps and baked buildings never set `guid` — and they are real persisted
placements with their own save files. Because `cap.Count == 0` the guarded push never runs, so
Ctrl+Z pops an **older unrelated action**.

### 3. Generated LOD1 meshes load back mirrored and inside-out — REPORTED
`game/LodBaker.cs:184`. `ObjMesh.Load` applies three conversions on read (Z-negation, UV V-flip,
winding reversal); `LodBaker` sources already-converted arrays and `WriteObj` emits them verbatim, so
`WorldBuilder` applies all three a *second* time on load. Retail-extracted `_lod1.obj` are in Unity
convention and convert exactly once — same filename, same loader, two different input conventions.
The agent flagged its honest limit: `content/objects/` is not in this checkout, so no baked artifact
could be eyeballed.

### 4. Closing the dev console recaptures the mouse under an open UI — REPORTED
`game/DevConsole.cs:73`. Tab to open the inventory, then backquote twice: the mouse is Captured while
the dashboard is still drawn, so the cursor is gone, the grid can't be clicked, WASD walks and held
LMB auto-fires through the open inventory.

### 5. Two menu panels stack on top of each other — REPORTED
`game/MainMenu.cs:235`. `HideAllPanels()` is called from one of five panel toggles; the other four
hand-hide a list and all omit `_graphicsPanel`. All four panels sit at the same screen position, so
Configuration → Play leaves both visible and whichever is later in child order takes the clicks.

### 6. Smaller, verified-by-reading
`DevConsole.cs:364` — an arg-length guard sits above `unarmed`/`fridge`/`fluid`/`survival`, so those
no-arg verbs are unreachable from the console. `MainMenuServers.cs:229` — a 1.5 s UDP query marshals

paths only null-check, and a freed node's C# reference is not null). `EditorBuildings.cs:396` —
undoing a wall delete drops six fields including the back-face material. `EditorSpawns.cs:372` —
