# Dropped item visuals

`entities/items.rs` ports `WorldItem.GetModel`, `MeshForAmount`, and `BuildReplicaVisual`; `entities::sync_world_items` consumes accepted world-item replicas. Dropped models come from `content/items/items_manifest.json`, independently of the held-model catalog. This restores real folded-shirt, pants, hat and other dropped models that previously disappeared when the held mesh field was null.

The original manifest supplies mesh, texture, flat color, source bounds, multi-round triangle cutoffs and material flags. Textures have generated mip chains with nearest filtering. Textured items retain source roughness .8, or .3 for the source `metal` flag (metallic remains0 intentionally). Flat-color meshes use .7 roughness. Missing models, including unknown catalog IDs, retain the source .24 m rarity-colored cube at .55 roughness. Source +90° X and deterministic NetId yaw are preserved.

Stack amounts use the original inclusive band rule and actual OBJ triangle prefixes; a change updates the existing entity and reuses cached prefix meshes. Pickup selection now traces the transformed original bounds enlarged15%, including off-center and wide clothing shapes. The selector never gives these visual replicas physical collision with players or bullets.

Four native tests load actual clothing and ammunition assets and verify real model/mipmap/material/focus behavior, original lower band boundaries, accepted amount changes without entity replacement, cached prefix reuse, authoritative removal, and visible/focusable rarity fallback for missing models/catalog entries. Managed profile tests also verify actual rarity/stack metadata. Live clothing drop/pickup evidence will be recorded with the inventory journey.

Remaining source behavior is explicit: `translucent` uses ordinary Bevy alpha blending; Godot's AlphaDepthPrePass is not yet reproduced. The original focus silhouette and floating rarity/name label are not implemented. The host-side dropped item's gravity/toss/settle body and accepted pose publication remain separate work; a replica does not simulate itself. Original `WorldItemReplicaView.BuildItemPuppet` does not mount gun attachments (the physical `WorldItem` does); this slice preserves that boundary and does not invent attachment state absent from the replica schema. Original per-item view-cone/occlusion culling also remains pending.

The depth-prepass target is the actual Godot **4.6-stable** renderer, rather than the stronger self-overlap claim in the `WorldItem.cs` comment. Its [forward clustered shader](https://github.com/godotengine/godot/blob/4.6-stable/servers/rendering/renderer_rd/shaders/forward_clustered/scene_forward_clustered.glsl#L1416) discards fragments below `opaque_prepass_threshold`; [the main scene sets 0.99](https://github.com/godotengine/godot/blob/4.6-stable/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp#L1791), while [shadow rendering sets 0.1](https://github.com/godotengine/godot/blob/4.6-stable/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp#L2770). The manifest currently marks six items translucent: Drinking Glass9301 has constant alpha112/255, Ice9347 has constant alpha204/255, and Pens9317/9318/9319/9343 contain alpha51..255. Thus glass/ice contribute no main depth-prepass pixels; the pens' opaque pixels do. All six have pixels above the shadow threshold. A faithful follow-up must reproduce these thresholds and subsequent alpha blending, not force depth writes for every transparent surface.

## Alpha-depth implementation plan (not linked)

Bevy0.20's `specialize_prepass_material_meshes` explicitly skips `AlphaMode::Blend`, and `MaterialPipelineKey` does not carry a general shadow-pass discriminator (both main depth and point-light shadows use the depth-prepass key). Guessing the pass from orthographic projection would silently fail for point lights. The following small adapter can use documented `MaterialExtension` controls without an engine fork:

1. Keep the original PBR alpha-blended color mesh, with `NotShadowCaster`. Its transparent color pass keeps depth writes disabled, matching Godot4.6 `SceneShaderForwardClustered`'s `DEPTH_DRAW_OPAQUE` behavior.
2. Add a colocated companion with `StandardMaterial::alpha_mode = Mask(0.99)` and a depth-only extension. Disable color writes in the main pass, preserve the depth prepass, and return `enable_shadows=false`. Thus the opaque texels establish depth before transparent color, without double-coloring them.
3. Add a shadow companion with `Mask(0.1)`, `enable_prepass=false`, and shadows enabled. Its main-pass specialization disables both color and depth writes; its shadow pipeline retains alpha-tested depth writes. Distinguish a prepass pipeline by the actual `PREPASS_PIPELINE` shader definition, not the camera projection. Both companion materials share the original texture and sampler. They need no collider or focus target.

Amount-prefix changes must replace all three mesh handles together; pose/rebase follows one common parent. Despawn must retire the complete group. Preserve source culling, render layers and any future skinning on companions. Specialization must visit every present optional color target, including an empty target list for shadows; it cannot assume `targets[0]` exists. Current Blend shadows discard below0.05, which happens to retain the same texels as0.1 for the six existing textures, but the exact adapter must still use0.1 for general content. The world/HDR reviewer found no ordering conflict: world postprocessing consumes the completed scene color/depth.

Required validation before claiming parity: actual material-specialization tests for color/depth writes and shadow/prepass flags; accepted amount-change/despawn tests including companion children; an offscreen threshold fixture spanning alpha0.05/0.099/0.1/0.989/0.99/1; then render and inspect overlapping real pens, glass and ice from two angles with a shadow receiver. The fixture must prove partially transparent pixels do not establish main depth and opaque pixels do, while0.1 survives the shadow pass. This is a proposed adapter, not a completed or visually verified feature.
